# ChatGPT checkout browser automation

Status: Superseded for production membership execution by [ADR-0006](./0006-go-headless-membership-checkout.md). The extension protocol remains only as legacy/reference behavior.

## Context

KaWang needs a controlled browser workflow for purchasing ChatGPT Plus, x5, or x20 with an eligible SpaceX Card. Card data is obtained from the SpaceX Card Open API. Each target ChatGPT account supplies a legitimately obtained Session and temporarily owns the single bound extension's sanitized incognito context through an exclusive browser lease.

The delivered system supports final checkout submission, but production activation is gated. The automatic-payment switch defaults off: first run a no-charge mode that exercises account eligibility, card-inventory and price discovery, checkout creation, target-plan/PH/PHP price validation, initial-page recognition, and field-location checks without final card selection or reservation, money movement, card-credential release, real-card autofill, or any post-card Next/final control activation; then enable explicitly scoped live canaries and expand only after controlled end-to-end confirmation. Later multi-step states are intentionally outside no-charge coverage. Dry-run success is not payment success.

Automatic checkout deliberately treats region and address as separate inputs: every initial membership checkout is created for country `PH` and currency `PHP`, while billing autofill reuses the existing KaWang `/api/public/us-address/generate` source, which returns a US Delaware record. The SpaceX Card `/gpt/checkout` API handles plan/region/currency link creation; it does not supply the billing address.

Generate a fresh US/DE person and address record for every checkout, even when a payment card is reused, rather than binding the generated name to the card. Automatic card opening obtains its required first and last name from its own generated record; later checkouts do not reuse that opening identity.

The automatic path treats an unavailable or incomplete KaWang address response as retryable `CHECKOUT_ADDRESS_UNAVAILABLE`. It does not fall back to `usaddressgen.com`, fill partial billing details, or submit checkout without the required address.

## Decision

Keep the existing session-activation delivery state machine unchanged: `extension_delivery_status` continues to mean only incognito Cookie installation, identity verification, refresh, and starting subscription protection. Create exactly one durable membership-fulfillment aggregate per redeem order for inventory readiness, eligibility, reservation, funding, checkout stages, reconciliation, final membership confirmation, and renewal cancellation. Store each stage execution as an append-only attempt; retry and operator resume increment a dedicated membership `resume_revision` and append evidence rather than creating another fulfillment, resetting status, or reusing the session-delivery attempt counter. The reservation, immutable funding intent, stage transaction snapshot, and all normalized provider evidence remain linked to that same aggregate across attempts. Neither state machine may overload or reset the other's status, and generic redeem-order status is not a substitute for payment-stage state. A membership fulfillment reaches `COMPLETED` only after the final target tier has strict dual confirmation and a subsequent membership query proves `auto_renew=false`.

Derive the customer-facing delivery result from membership fulfillment, never from successful session activation or an intermediate Plus stage. Show success only for `COMPLETED`. Present `PARTIALLY_FULFILLED` as “人工处理中” and `PARTIAL_FULFILLMENT_EXPIRED` without a compensation resolution as “售后处理中”, without exposing card, provider, or payment internals. Once an audited customer-compensation resolution exists, present its corresponding safe result—“已退款”, “已补发”, or “已协商完成”—while preserving the underlying expired partial fulfillment unchanged.

Reuse KaWang's existing Feishu Webhook notification path and add a prominent operations-console task for fulfillment states that require intervention. Notify only on normalized critical classes: local human payment action, unknown or uncertain money outcomes, partial or expired partial fulfillment, renewal-cancellation failure, and an opened dependency circuit. Deduplicate delivery by membership fulfillment, normalized state, and state revision so worker retries do not spam the same event; a genuine state revision may notify again. Messages contain only order-safe identifiers, target tier, normalized reason, state time, and the required operator action—never Session/Cookie data, email, card details, billing data, provider payloads, checkout URLs, or credentials. Acknowledging a notification does not alter payment evidence or advance the state machine.

Use one exclusive browser-fulfillment lease for the single bound extension installation and its shared incognito Cookie Store. Inventory pulls, webhook reconciliation, card-segment price refreshes, and other read-only preparation may run concurrently, but a queued order cannot finalize a card reservation, open a card, recharge, or enter checkout until it owns this lease. Do not pre-fund a backlog while browser activation remains serial. Lease loss follows the existing no-money versus money/unknown recovery boundaries and never enables a second order to overlap an unsanitized incognito context.

Independently enforce one active membership fulfillment per verified ChatGPT identity across all orders. Derive the lock key from the stable verified account identifier when available, otherwise from the normalized email proven by the imported Session; persist only the existing protected identity data and a non-reversible keyed lock value, never an email in lock or queue logs. A later order for the same identity enters `ACCOUNT_FULFILLMENT_WAIT` before card selection, reservation, funding, or checkout. After the earlier fulfillment reaches a terminal outcome, wake the waiter and repeat the authoritative starting-membership and purchase-eligibility checks from scratch; do not assume that terminal failure left the account free or that terminal success permits another purchase. The account lock is separate from the global browser lease and remains effective across worker or service restarts.

1. Before enabling automatic checkout, an administrator starts a resumable full inventory initialization. Import all owned cards and reconcile each card's history; expose progress, isolate anomalous cards in reconciliation hold, and keep automatic selection disabled until the initial run completes.
   After initialization, consume signature-verified SpaceX Card transaction webhooks as prompt signals and combine them with targeted authoritative pulls for active, changed, or uncertain cards plus a full inventory reconciliation every six hours. Deduplicate webhook state transitions and discard the webhook's full card number rather than persisting or logging it; map events by upstream card and authorization identities.
2. Snapshot the product's explicit target membership tier (`plus`, `x5`, or `x20`) onto the redeem order; never infer it from a site slug, title, or CDK prefix.
   Before any card reservation or funding, obtain the normalized starting membership. Continue immediately for a free account. A delinquent account must first complete renewal protection and confirm `auto_renew=false`, then prove current replacement-purchase eligibility by generating the initial Plus link and recognizing a Plus checkout surface with PH/PHP and the expected amount. Delinquency flags alone are insufficient. If that proof is unavailable, enter `ACCOUNT_REPURCHASE_NOT_READY` without opening, recharging, or paying; retry the membership query and checkout proof later. Put a healthy existing Plus/x5/x20 membership in `ACCOUNT_ALREADY_SUBSCRIBED` without spending.
3. Acquire the exclusive browser-fulfillment lease, sanitize the shared incognito authentication-cookie allowlist, and open the target account in a fresh incognito window. Do not create a persistent per-account browser profile.
4. Import and validate that account's Session without writing Session secrets to ordinary logs.
5. Have kwRedeem call the fixed SpaceX Card `/api/v1/gpt/checkout` adapter with the protected order session and `plan_name=plus`, `country=PH`, `currency=PHP`; return only the resulting one-time checkout URL to the extension. The extension does not extract or transmit a ChatGPT access token to create the checkout.
6. Fetch candidate cards from SpaceX Card, then fetch real-time details for candidates.
7. Reconcile existing cards from their per-card OpenAI transaction history, deduplicated by upstream authorization identity. For initialization only, pair each final x5/x20 payment with the nearest preceding unpaired Plus payment on the same card within two hours. Cards with no recognized membership fulfillment remain unassigned; Plus-only fulfillments enter the Plus lane, while valid staged pairs enter their final x5 or x20 lane. Missing, late, conflicting, mixed-final-tier, over-capacity, or otherwise unclassifiable histories enter a reconciliation hold. New KaWang orders use their durable order and reservation identity instead of time-based pairing.
8. Exclude cards that fail the configured eligibility policy and atomically reserve one capacity slot for the order before funding or checkout. An unassigned card is provisionally lane-locked by that reservation. Release it only after proving that no OpenAI payment occurred; retain any paid or uncertain reservation for reconciliation, and consume it on final fulfillment success.
   Among eligible cards, first consolidate an existing target-lane card and rank those cards by the smallest real-time funding shortfall. Use an unassigned card only when no same-lane card has capacity, and open a new card only when neither class is available.
   Automatic opening is limited to administrator-allowed product codes that are proven by an existing same-product card with complete price signals for the order's required stages, all no more than 72 hours old. Rank proven products by total funding cost; if none exists, pause before spending rather than opening an untested product.
9. Read the selected card segment's latest matching amount for every required tier from `GET /cards/{id}/openai-payments`, then add a fixed USD 0.20 to each effective payment stage. A Plus order uses `plus.amount + 0.20`; an x5/x20 order sums `plus.amount + 0.20` and the final tier's `amount + 0.20`. Do not add a separate configured price floor or choose a random allowance.
   A candidate is ineligible when any required tier returns `found=false` or its reported `time` is more than 72 hours old; try the next candidate. If every candidate lacks a complete fresh price signal, place the order in `CARD_PRICE_UNAVAILABLE` before any recharge, card opening, or browser checkout.
10. Before any card opening or recharge, complete every non-funding prerequisite that is reachable before the initial Plus purchase: validate the protected Session and starting-account eligibility, finish renewal protection when required, verify inventory readiness and the target-tier configuration, select and reserve an eligible card or proven product, synchronize all required prices and balances, create the initial Plus checkout link and fresh address, activate the isolated incognito session, and recognize the initial checkout surface including its expected plan, PH/PHP context, displayed amount, required fields, and allowlisted submit control. Validate the displayed current charge against an active, administrator-approved, versioned PHP minimum/maximum range for the stage's tier; snapshot that contract version onto the stage. Missing configuration or an out-of-range amount enters `CHECKOUT_PRICE_UNRECOGNIZED` without funding. This PHP UI contract is independent of the selected card segment's USD payment history: do not convert currencies or compare them directly. A failed or unavailable prerequisite exits or waits without moving money; do not fund first and discover an initial-stage browser or integration incompatibility afterward. For x5/x20, the final plan-management and upgrade-checkout surfaces do not exist until Plus is active, so their validation is an explicit post-Plus stage gate rather than a claim that they were preflighted before funding.
11. After that pre-funding gate passes, synchronize the selected card's real-time available balance again and fund only the shortfall for the full order. Before calling SpaceX Card, durably insert one immutable funding intent containing the operation type, target card or product, exact amount and body fingerprint, and a non-secret deterministic idempotency key such as `kwr:{orderNo}:open:v1` or `kwr:{orderNo}:recharge:v1`. The database commit must precede the external write. Skip recharge when the real-time balance is already sufficient, and do not recharge between upgrade stages.
   When no existing card can be used, set a proven product's opening `init_amount` to the greater of its minimum amount and the full order budget. The opening itself is the order's single funding operation; do not follow it with a recharge. Reject products whose maximum is below the required amount, and open only when the SpaceX Card platform balance covers `open_fee + init_amount`.
   If the platform balance cannot cover an existing-card recharge including its fee, or a new card's `open_fee + init_amount`, release any reservation for which no payment occurred and place only that order in `PLATFORM_BALANCE_INSUFFICIENT`. Continue cheaper or already-funded orders and allow timed or manual retry.
   A timeout, disconnected response, or otherwise unknown write result enters `FUNDING_OUTCOME_UNKNOWN` and blocks checkout. Recovery may only replay the persisted operation with the identical body and idempotency key so SpaceX Card returns the original result; it must never recalculate the amount, generate another key, infer success solely from balance changes, or create a second funding intent. Validate a replayed success against the intended card/product and amount before advancing.
12. Fill and submit only through a versioned checkout state-machine adapter that revalidates the page origin, expected plan, Philippines/PHP context, displayed amount, every required field, and explicitly allowlisted controls. Support recognized multi-step variants in which filling card or billing details reveals a separate Next/Continue control: classify that control as a checkout progression control from its versioned state, selector, surrounding structure, and expected destination—not button text alone—and never treat it as the final payment control. Before the first post-card control activation, snapshot the card's authorization identities. After each progression click, require the expected next state within a bounded time and revalidate the checkout facts. Any new transaction at this point—including an OpenAI `$0`, `$1`, or other small verification authorization—enters `UNEXPECTED_PREAUTH`, retains the order and reservation for reconciliation, and blocks the final payment click; do not assume an amount is harmless or add it to an allowlist without stable production samples and a versioned adapter update. Detect repeated states and cap transitions so an adapter bug cannot click in a loop. Only the separately allowlisted final payment control may submit the charge, and it requires one last full validation immediately before activation. An unknown or changed state enters `CHECKOUT_UI_UNSUPPORTED` without another click; do not reuse the existing broad text-scoring heuristic. Then confirm the stage from both ChatGPT's expected membership state and the matching non-declined SpaceX Card OpenAI payment. Page text or either provider signal alone is insufficient. A missing or timed-out signal enters uncertain-payment reconciliation and must not trigger another automatic submission.
   For the ChatGPT side, kwRedeem posts `{ "token": <decrypted session object> }` from the server to the fixed, authorized `https://gptserve.freespaces.app/api/subscription/info` adapter and validates its structured account type. The extension does not call this service or receive the Session; KaWang stores only normalized confirmation fields and never persists or logs the raw request or response.
   Strictly normalize provider account types as `free → free`, `plus → plus`, `prolite → x5`, and `pro → x20`; do not assume the provider returns KaWang's `x5` or `x20` product labels. A null, empty, or unknown value enters `MEMBERSHIP_CONTRACT_UNKNOWN`, opens the membership-provider circuit for new money, and must never be inferred as free. Add another value only after a real response sample has been safely reduced to a non-sensitive contract fixture and the adapter is versioned.
   A valid membership-side stage response requires envelope `code=200`, the expected normalized account type, `currency=PHP`, both overdue/delinquent flags false, and a parseable future `expire_time`. After final renewal cancellation it additionally requires `auto_renew=false`. Missing or malformed fields remain uncertain rather than weakening the predicate.
   An `Authorization/PENDING` card event may satisfy the card side when the membership predicate also succeeds. Consume capacity immediately and continue tracking it; a later settlement completes reconciliation, while a later decline or reversal enters review without an automatic replacement payment.
   Immediately before submission, snapshot the reserved card's existing authorization identities. Poll for at most five minutes after submission and require exactly one new OpenAI transaction in the current tier's documented amount range with `PENDING` or `COMPLETE` status. No match or multiple matches enter `PAYMENT_OUTCOME_UNCERTAIN`; never substitute the card's merely latest transaction.
   A new matching `DECLINED` transaction is a known non-payment only when the membership provider still reports the verified pre-stage state and reconciliation proves no other effective payment exists. Enter `PAYMENT_DECLINED` without automatically resubmitting, switching cards, or moving more money. The funded card and its balance remain unchanged; never delete or freeze it. KaWang exposes only evidence recheck, never a management action that submits another payment. If no stage has ever been paid, explicitly release the internal capacity reservation after that proof and finish automatic membership fulfillment as failed. If an x5/x20 order's Plus stage was already paid and only the final upgrade declined, retain the reservation and enter `PARTIALLY_FULFILLED` for operator resolution without repeating Plus. An operator may act outside KaWang and later request another authoritative recheck; KaWang completes only if the same reserved-card and membership evidence satisfies the normal strict predicates, and it does not weaken them to recognize an unrelated external payment.
   If page loading, autofill, or a recognized intermediate transition fails before final submission, first prove that the final payment control was never activated, membership remains at the pre-stage state, and the authorization snapshot has no new transaction. Reuse the same reserved card and existing balance, regenerate the link and fresh address as needed, and retry the stage at most three times without switching cards or funding again. After three failures enter `CHECKOUT_PRE_SUBMIT_FAILED`, retain the reservation and funded balance, and wait for an adapter fix or operator resume. Any inability to prove the non-payment predicate uses uncertain-payment handling instead.
13. A Plus order completes after its Plus stage is confirmed. An x5/x20 order confirms the initial Plus stage, returns to the versioned ChatGPT plan-management surface, and uses an explicitly allowlisted target-specific control to change to x5 or x20. It does not request a direct `/gpt/checkout` link with `plan_name=prolite` or `plan_name=pro`. Before entering card details or submitting the second payment, validate the plan-management page, selected target tier, resulting PH/PHP upgrade-checkout page, displayed final-tier amount against that tier's active versioned PHP price contract, required fields, and allowlisted submit control; snapshot the final stage's contract version at this gate. An unknown or changed management/upgrade surface enters `UPGRADE_CHECKOUT_UNAVAILABLE` with the already funded card and reservation retained; retry only navigation and validation, never funding or a prior payment. Apply the same dual confirmation to the final tier after submission.
14. After the final target tier is confirmed, call the existing cancellation adapter to disable the newly enabled automatic renewal and query membership state again until `auto_renew=false`. Do not cancel between the Plus and upgrade stages. If an x5/x20 final upgrade explicitly declines and enters `PARTIALLY_FULFILLED`, initially leave the confirmed Plus renewal setting unchanged while awaiting external completion and surface the enabled-renewal risk prominently. This exception is time-bounded: as soon as the confirmed Plus `expire_time` is no more than 72 hours away, automatically invoke renewal cancellation and keep querying until `auto_renew=false`; cancellation failure retries and alerts through the renewal-recovery path, never another payment. The order remains `PARTIALLY_FULFILLED`, retains its paid evidence and card reservation, and must not be reported as x5/x20 merely because Plus renewal is now disabled. If authoritative membership evidence later proves that Plus has expired without the target x5/x20 tier being established, enter terminal `PARTIAL_FULFILLMENT_EXPIRED`: retain the paid-stage evidence and occupied card capacity, prohibit automatic Plus repurchase, upgrade payment, recharge, or reservation release, and require an explicit external customer-compensation resolution. Keep that compensation resolution separate from the immutable payment outcome. The operations console may append `REFUNDED`, `REPLACEMENT_DELIVERED`, or `CUSTOMER_ACCEPTED_PARTIAL` together with the operator identity, server timestamp, and an external evidence/reference identifier; it must not execute the refund, replacement payment, card operation, or capacity release. Corrections append another audited resolution revision rather than rewriting history. If external handling establishes the final target tier before expiry, perform the normal final cancellation and confirmation then. If final payment succeeded but renewal cancellation is unavailable, retain the consumed slot and retry only query/cancellation; never submit payment again.
15. Consume or retain the card reservation according to the confirmed or uncertain outcome; release it only after proving no payment occurred. A reservation release is purely an internal scheduling operation: it ends the order-to-slot claim (and, for a previously unassigned card, its uncommitted provisional lane claim) without deleting, freezing, refunding, or otherwise changing the SpaceX Card card or balance. An existing committed membership lane is never removed by releasing another order's reservation.
   When the fifth Plus, second x5, or first x20 slot is consumed, mark the card internally as `CAPACITY_FULL` and exclude it from future membership selection. Leave the upstream card `ACTIVE` and leave its remaining balance untouched; do not automatically refund, freeze, or delete it. Any later balance recovery is an explicit administrator action outside automatic fulfillment.
   Resolve uncertain, preauthorization, and lost-challenge outcomes only from authoritative evidence. Management actions may request immediate reconciliation or leave the case pending, but must not force success, failure, or capacity release over missing or contradictory provider facts. Success still requires the strict membership-and-transaction pair. A no-payment resolution requires the verified pre-stage membership state plus proof that no effective transaction exists and that every related authorization is absent, declined, or fully reversed, with no pending or completed charge. When a recorded final-submit activation produces no transaction at all, perform full authoritative card-history and membership checks at approximately five minutes, one hour, and 24 hours after submission. Only if all three retain the pre-stage membership and show no new OpenAI transaction or pending authorization may the management UI enable an operator-reviewed “确认未扣款并释放预留” action after 24 hours; it never releases automatically. Persist only normalized evidence references and the reconciliation decision in the audit trail, never raw provider responses or secrets.
16. Apply the ordinary 24-hour task deadline only while no card-opening request, recharge request, or payment submission has been made. If that deadline expires, end the task and release its no-payment reservation. Once any such money-affecting request has been issued—including a request whose result timed out or is unknown—do not automatically expire the task, release its capacity, or resubmit payment; keep it in reconciliation until the outcome is proven and then converge it explicitly.

## Safety and reliability boundaries

- SpaceX Card API credentials, full PAN, CVV, billing address, and imported sessions are secrets and must not appear in source control or ordinary logs.
- The KaWang operations console may start/resume inventory initialization, refresh inventory/prices/balances, display masked card lane/capacity/hold state, configure allowed products and versioned PHP price contracts, request reconciliation, and resume only evidence-permitted workflow states. It must not expose direct open-card, recharge, card-balance refund, freeze, or delete commands; those would bypass the order reservation and immutable funding-intent invariants. Exceptional manual money management remains in the official SpaceX Card console and is later observed through reconciliation.
- Keep the SpaceX Card GPT user token, OpenAPI `app_secret`/optional `app_id`, and Webhook signing secret as separate encrypted settings with non-overlapping call sites. The GPT token is only for `/api/v1/gpt/*`; OpenAPI credentials are only for `/openapi/v1/*`; the Webhook secret is only for raw-body signature verification.
- KaWang stores only the upstream card identity, masked display data, and scheduling metadata needed for eligibility, capacity, and reservation. It fetches the full PAN, expiry, CVV, and billing details only after reserving a card, keeps them in memory for the active checkout, and never persists them in its database or browser storage.
- Deliver full card details to the extension only through a short-lived HTTPS REST material grant bound to the membership fulfillment, stage, attempt, browser lease, one installation identity, and an unpredictable single-use nonce. Authorize it only after the current stage's gates allow autofill; set `Cache-Control: no-store`, cap the response size, and return the full card details, fresh address, checkout target, and validation metadata only in that response. WebSocket messages remain non-sensitive wake-up notifications. The extension keeps the material in the current execution memory, never writes it to `chrome.storage`, IndexedDB, logs, errors, or another network service, and discards it immediately when the attempt leaves autofill/checkout. If the worker, tab, or response is lost, a new grant requires fresh authentication plus proof that no payment or unexpected authorization occurred; never revive or replay an old grant blindly.
- For `CHECKOUT_UI_UNSUPPORTED`, accept only a size-bounded structured diagnostic containing the adapter/version and state identifiers, allowlisted origin and normalized route template, normalized target tier/currency/displayed amount, booleans for expected element presence, and a non-reversible structural DOM hash. Reject and never collect raw HTML, text dumps, screenshots, input values, email, address, PAN/CVV, Cookie, Session, access token, or arbitrary extension error details. Treat this fingerprint as debugging evidence only, never as permission to click.
- Package checkout and plan-management adapters in the reviewed extension release. Their selectors, structural predicates, state transitions, progression controls, and final-payment allowlist are code, not mutable server settings. The server may require a minimum extension and adapter version and pause incompatible work, but it must never supply replacement selectors, button-text rules, or JavaScript for execution on payment pages. Supporting a new fingerprint requires an extension code change, tests, and version bump before processing resumes.
- SpaceX Card webhooks are authenticated from the raw request body with the configured signing secret. Their full card-number field is never persisted or logged; durable reconciliation uses upstream card and transaction identities.
- Card capacity counts final membership fulfillments, not raw OpenAI transactions: a Plus card serves up to five Plus orders, an x5 card serves up to two x5 orders, and an x20 card serves one x20 order. The initial Plus payment in an x5/x20 staged upgrade does not consume a separate Plus slot.
- A declined transaction or a pre-settlement authorization reversal may release a reservation only after reconciliation proves there is no other effective payment. A post-settlement refund does not automatically restore capacity; retain the slot and place the card in refunded-fulfillment review.
- Card deletion and card freezing are outside the fulfillment workflow. Internal eligibility, reservation, and reconciliation states must not invoke either upstream operation.
- The single incognito Cookie Store is shared only over time: one account owns it through the exclusive browser lease, and the extension sanitizes the authentication-cookie allowlist before another account may use it. Separate incognito windows are not separate profiles.
- CAPTCHA, 3DS, SMS verification, and other security challenges are explicit human-handoff states. The automation will detect and pause; it will not bypass or disguise automation to evade those controls.
- A challenge enters `PAYMENT_ACTION_REQUIRED` while retaining the active page, order, and card reservation. After the operator acts, resume only membership/transaction confirmation; do not switch cards or submit another payment.
- Present the challenge and its local resume control in the extension that owns the incognito tab. After completing the visible challenge, the operator clicks “已完成验证，继续核对”; record only the order, extension installation identity, normalized challenge type, and server timestamps. That acknowledgement is not evidence of success and permits only membership and card-transaction confirmation. Do not provide a remote management-page control that can blindly advance a browser it cannot observe, and do not infer acknowledgement solely from DOM navigation.
- Because Chrome incognito windows share one incognito Cookie Store, `PAYMENT_ACTION_REQUIRED` pauses the entire browser activation queue. Opening another incognito window is not account isolation and must not permit a second order to overwrite the active session.
- If the owning incognito tab, window, or browser disappears during `PAYMENT_ACTION_REQUIRED`, enter `ACTION_REQUIRED_CONTEXT_LOST`. Never recreate the checkout or resubmit payment, and retain the order and card reservation while the server continues membership and card-transaction reconciliation. The extension must clear the affected incognito authentication-cookie allowlist and verify the store is sanitized; after that it may release the global browser-queue pause and process another order because reconciliation no longer depends on the lost page. A failed cleanup remains a global cookie-safety pause under the existing rollback rules.
- Linux-hosted browsers may be used for repeatable deployment, but browser-fingerprint spoofing is outside this design.
- Deploy the final-payment capability behind a default-off production rollout gate. Opening it requires completed inventory initialization, valid credentials and price contracts, a compatible extension/adapter version, successful no-charge validation, and an explicitly scoped live canary; broad enablement follows observed end-to-end success rather than deployment alone.
- No-charge validation must never fetch or expose full card credentials, create a final capacity reservation, open or recharge a card, populate a real PAN/CVV, or activate a control that appears only after card entry. In particular, it cannot click a checkout progression control because that action may create a zero- or small-value verification authorization. It validates only the states reachable without a real payment instrument; live canaries supply evidence for later states.
- While in live-canary mode, authorize final payment by explicit redeem order only and allow at most that one approved order through the money/submit gate at a time. Creating the authorization requires a currently authenticated administrator to re-enter and successfully verify their login password for that action; never persist the confirmation password or include it in audit details. Record the administrator username and server time with the immutable approval snapshot. The extension, fulfillment worker, scheduler, and browser adapter have no capability to approve their own work. Do not select canaries randomly, infer approval from product membership, or automatically promote a successful canary into site/product-wide enablement. Any later broad scope is a separate audited administrator decision.
- Bind each live-canary authorization to an immutable snapshot of the order and target tier, selected upstream card identity, exact funding budget, active PHP checkout-price contract version, and required extension/adapter version. Any mismatch or later change invalidates it and requires a new administrator decision. Atomically consume the authorization immediately before the first final-payment control activation; it is single-use and cannot authorize a retry, later stage, or altered checkout. For x5/x20, the final upgrade is a separate payment stage and therefore requires its own explicit canary authorization and fresh password confirmation after the Plus stage is confirmed and its final checkout facts exist.
- A prepared canary stage may retain its incognito page and browser lease for at most 15 minutes while awaiting the matching authorization. On expiry, invalidate the checkout/approval snapshot, discard ephemeral material, sanitize the incognito authentication-cookie allowlist, and release the global browser queue. Retain the membership fulfillment, reserved card, existing balance, funding intent, and every confirmed prior stage. A later resume reacquires the lease, revalidates membership and transactions, and rebuilds only the current unpaid stage with a new approval snapshot; it never repeats Plus, recharge, or another confirmed action.
- Qualify broad automation independently for each target tier, exercised checkout-adapter path and version, and active PHP checkout-price contract version. A qualifying live canary must finish the entire tier flow, reach card transaction `COMPLETE` rather than relying only on provisional authorization, confirm the exact final membership, prove `auto_renew=false`, and leave no unresolved preauthorization, payment, refund, or adapter outcome. Every target-tier canary is self-contained and requires no qualification from another order: Plus performs its single stage, while x5 and x20 each perform their own same-order Plus stage and target-specific upgrade stage with separate approvals. The intermediate Plus stage of an x5/x20 fulfillment is not a separate Plus order and does not create a global Plus qualification. A completed canary qualifies only its exact target tier; a single-page path does not prove an unexercised multi-step path, and evidence from an older adapter or price contract does not qualify a new version. Qualification only enables the administrator to create a separately audited product/site rollout scope; it never expands scope automatically. Each tier remains independently enabled and may be paused without enabling, disabling, or requalifying another tier.
- Version every product/site automatic-checkout scope and record its activation time. On first activation, default the scope to one order per business day and prefill its USD risk limit from the funding planner's current complete one-order estimate for that exact tier, including the applicable provider funding fee; do not enable when no complete estimate exists or when the entered limit is below it. Creating or re-enabling a scope requires a currently authenticated administrator to re-enter and successfully verify their login password, then explicitly confirm the exact site, product, target membership tier, extension/checkout-adapter version, PHP checkout-price contract version, positive daily order limit, and positive daily USD risk-budget limit. Persist those facts together with the administrator username and server time, but never the confirmation password. Increasing either limit requires another fresh password confirmation and creates a new audited scope revision; it never edits the active revision in place. Qualification never creates or enables the scope automatically, and there is no unscoped master switch that bypasses this decision. The scope applies only to matching eligible orders created after activation; older queued orders remain canary-only and require explicit per-order authorization. Publishing or activating a different adapter or PHP price-contract version automatically pauses every matching scope before another fulfillment can cross the money boundary. That new version must complete no-charge validation and its own qualifying live canary before an administrator may freshly authenticate and enable a replacement scope revision. Already money-bearing fulfillments retain their snapshotted old contracts for safe convergence rather than being abandoned or silently migrated.
  Immediately before a matching fulfillment first crosses the funding boundary, atomically consume one order unit and reserve its full snapshotted USD payment budget plus any applicable card-opening or recharge fee from that scope's business-day risk budget. Count the full payment budget even when an existing card balance makes the actual recharge zero, because payment exposure still exists; x5/x20 reserves the combined Plus and final-stage budget once. Hitting either limit blocks new money actions and emits a fulfillment-intervention alert, but does not interrupt reconciliation, renewal cancellation, or safely authorized remaining work for a fulfillment that already consumed its quota. Worker retries and later stages reuse the original quota reservation rather than counting again. A quota reservation may be released only while the fulfillment proves it never issued a card-opening, recharge, or final-payment request; after crossing any money boundary, do not restore it automatically from a decline, refund, or uncertain outcome. Disabling a scope follows the same boundary: it prevents matching work that has not consumed quota from moving money but does not abandon money-bearing state.

A checkout/plan-management adapter mismatch blocks only the affected adapter version, tier, and path. Session/account eligibility, explicit decline, or another account-specific outcome stays on that fulfillment. Circuit opening never disables authoritative read-only reconciliation or renewal-cancellation recovery for money-bearing fulfillments; those continue with bounded retry and visible alerts. Record normalized circuit reason, scope, timestamps, and recovery revision without upstream bodies or secrets.
