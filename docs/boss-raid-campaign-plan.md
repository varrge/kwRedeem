# 全站 Boss 突袭月度活动策划案

- 状态：规则已确认，待实现
- 版本：1.0
- 日期：2026-08-19
- 时区：`Asia/Shanghai`
- 一期范围：单个 Sub2api 连接

## 1. 策划结论

该活动值得做，但必须同时兑现两种承诺：所有有效参战者共同击败 Boss 并获得共享奖励，贡献最高的玩家再获得按参与人数浮动的 MVP 奖励。若只有头部排名奖励，活动会退化为月度消费榜，普通用户缺乏持续输出的理由。

攻击不额外扣除额度。玩家加入活动后，正常调用 API 产生的真实额度消耗会自动转换为伤害。活动页面负责呈现服务端已经确认的伤害、排行和奖励，不负责决定或制造伤害。

活动每个自然月开启一次，从 Boss 1 开始连续推进。每只 Boss 独立计算贡献、有效参战人数、获奖名额和奖励；击败后结算并进入下一只，贡献不跨 Boss，进度不跨月。

## 2. 活动目标

### 2.1 主要目标

1. 提高全站真实 API 额度消耗，而非充值或人为扣款。
2. 通过主题伤害倍率引导用户使用指定 Sub2api 分组或与其稳定映射的中转站。
3. 建立每月一次、可持续复用的全站协作事件。
4. 在活动开始前锁定最坏奖励成本，避免临时缩奖或超预算。
5. 让普通用户、大额用户和运营方都能看到明确、可审计的活动结果。

### 2.2 非目标

- 不通过“攻击”按钮直接扣除用户余额。
- 不把充值、兑换码、邀请返利、管理员调账或世界杯余额变动算作伤害。
- 一期不跨多个 Sub2api 连接聚合。
- 不无限生成 Boss；打完配置中的最后一只即全服通关。
- 不承诺逐请求实时动画；权威用量同步最多允许约 60 秒延迟。
- 不在活动中途修改血量、门槛、主题倍率或奖励。

## 3. 核心循环

```text
每月开始
  -> 玩家主动加入
  -> 正常 API 使用产生权威用量
  -> 实际消耗 × 主题倍率 = Raid Damage
  -> 全站共同削减当前 Boss 血量
  -> Boss 进入最终同步与结算
  -> 冻结贡献榜、有效人数和奖励
  -> 发放共享奖励与 MVP 奖励
  -> 开启下一只 Boss
  -> 最终 Boss 被击败或月份结束
```

活动的协作层由 Boss 血量和共享奖励提供，竞争层由 Boss 级贡献榜和浮动 MVP 名额提供。两层使用同一份伤害事实，但分别解决“愿意参与”和“愿意多贡献”两个问题。

## 4. 时间与活动状态

### 4.1 月度时间

- 每月 1 日 `00:00:00` 开始。
- 次月 1 日 `00:00:00` 停止接收新伤害。
- 月末后进入 10 分钟结算窗口，只补同步月末前已经发生的权威用量。
- 结算窗口内页面显示“本月战斗结算中”，不把次月用量计入上月。
- 玩家加入状态只持续当前自然月，下月需要重新加入。

### 4.2 活动状态

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `draft` | 草稿 | 编辑 Boss、门槛、倍率、奖励与预算 |
| `scheduled` | 已发布待开始 | 只读，可在开始前撤回为草稿 |
| `active` | 战斗中 | 加入、同步伤害、查看排行 |
| `settling` | 最终同步或月末结算 | 只读，不接收新伤害 |
| `cleared` | 最后一只 Boss 已击败 | 展示通关结果并完成剩余发奖 |
| `ended` | 月份正常结束 | 查看历史结果 |
| `aborted` | 数据或履约异常导致中止 | 保留已结算奖励，当前 Boss 不正常派奖 |

提前中止不等同于正常结束。此前已经结算的 Boss 奖励继续履约；正在战斗的 Boss 不产生正常共享奖励或 MVP 奖励。运营补偿必须另建有审计记录的补偿单，不能伪造击杀或改写排行榜。

## 5. 参战资格

1. 用户账号必须在当月活动开始前已经注册。
2. 用户可在当月任意一只 Boss 存活期间主动点击“加入战斗”。
3. 只计算加入时间之后发生的合格用量，不追溯加入前消费。
4. 加入一次后，本月后续 Boss 自动保持参战状态。
5. 同一稳定 Sub2api 用户 ID 下的所有 API Key 消耗合并统计。
6. 内部账号、测试账号和管理员配置的排除账号不参与伤害或获奖。
7. 用户只需正常使用 API；战斗页不提供额外扣款的攻击按钮。

## 6. 伤害规则

### 6.1 权威来源

伤害只来自远端官方 Sub2api 管理用量接口的逐条记录。每条记录至少需要：

- 稳定且可去重的远端用量 ID；
- `user_id`；
- `actual_cost`；
- `created_at`；
- 可选的 `group_id` 和 `subscription_id`。

不得用余额前后差额推算伤害。Boss 系统也不能只读取现有 `sub2api_shake_consumptions`，因为该表只保留命中摇摇乐资格规则的消费，并非全站消费总账。

### 6.2 计算公式

```text
基础伤害 = 远端用量记录的 actual_cost
最终伤害 = 基础伤害 × 该记录命中的活动主题倍率
```

- 默认主题倍率为 `1.0x`。
- 最终伤害统一规范化到 8 位小数。
- 真实限时计费倍率已经反映在 `actual_cost` 中，因此活动始终按用户实际扣费计算。
- 活动主题倍率只增加 Boss 伤害和个人贡献，不改变用户账单。
- 最终伤害同时用于 Boss 血量、有效参战门槛、排行榜和 MVP 结算。
- 页面同时展示“实际消耗”和“主题加成伤害”，避免用户误解账单。

### 6.3 主题分组

一期只对权威用量记录可识别的 Sub2api `group_id` 配置主题倍率。运营页面可以展示该分组对应的中转站名称，但只有存在稳定的一对一映射时才能称为中转站加成；若远端记录不能证明具体中转站，就不能按前端选择或推测计分。

不同 Boss 可配置不同主题分组，例如：

| Boss | 普通分组 | 指定分组 |
|---|---:|---:|
| Boss 1 | `1.0x` | `1.0x` |
| Boss 2 | `1.0x` | `1.25x` |
| Boss 3 | `1.0x` | `1.5x` |

所有倍率在活动发布后锁定。

### 6.4 Boss 边界与溢出伤害

- 用量按权威 `created_at` 排序并分配，不能按同步到本地的时间分配。
- 同一时间的记录使用稳定远端用量 ID 作为确定性次序。
- 单条用量不可拆分。
- 若 Boss 剩余 5 点血量，一条记录造成 100 点伤害，则该 100 点全部计入当前 Boss。
- 95 点溢出伤害不顺延到下一只 Boss。
- 下一只 Boss 只接收已确认击杀边界之后发生的用量。
- Boss 达到零血后先进入最终同步；连续两次同步没有更早的新增记录后才冻结结算快照并开启下一只。
- 极端情况下若结算后发现远端回填的更早记录，不改写已冻结榜单，进入异常审计和独立补偿流程。

## 7. Boss 配置与数值

每月使用管理员配置的逐级 Boss 表，不锁死线性或翻倍公式。单只 Boss 至少配置：

- 顺序与等级；
- 名称、称号和内置素材；
- 最大血量；
- 主题分组及伤害倍率；
- Boss Clear Reward；
- 第 1、2、3 名的 MVP Reward；
- 奖励内部成本和发放模式。

一期建议 4 只 Boss，以下仅作首月模拟值：

| 等级 | 血量 | 定位 | 主题倍率示例 |
|---|---:|---|---:|
| Boss 1 | 2,000 | 低门槛开场，验证参与率 | `1.0x` |
| Boss 2 | 4,000 | 引导指定分组 | `1.25x` |
| Boss 3 | 7,000 | 中段协作目标 | `1.5x` |
| Boss 4 | 11,000 | 月度最终 Boss | `1.5x` |

正式血量应在上线前使用最近三个月的同周期真实消耗回放。首月目标应让 Boss 1 在活动早期被击败，同时确保最终 Boss 需要显著增长才能通关。活动开始后不得根据实际进度临时加血或减血。

## 8. 有效参战与排行榜

### 8.1 有效参战门槛

- 每月配置一个统一的个人伤害门槛，建议首月默认 `10`。
- 玩家每只 Boss 都需要重新达到该门槛，加入状态本身不重置。
- 门槛按包含主题加成后的最终伤害计算。
- 低于门槛的伤害仍削减 Boss 血量，但该用户：
  - 不计入有效参战人数；
  - 不增加 MVP 名额；
  - 不获得共享奖励；
  - 不进入最终获奖候选名单。

### 8.2 浮动 MVP 名额

```text
MVP 名额 = min(3, floor(有效参战人数 / 10))
```

| 有效参战人数 | MVP 名额 | 获奖者 |
|---:|---:|---|
| 0–9 | 0 | 无 MVP 奖励 |
| 10–19 | 1 | 第 1 名 |
| 20–29 | 2 | 第 1–2 名 |
| 30+ | 3 | 第 1–3 名 |

少于 10 人时仍可发 Boss Clear Reward，但不发 MVP Reward。

### 8.3 排名规则

1. Boss Contribution 降序。
2. 贡献相同时，较早达到最终贡献值者优先。
3. 若权威时间仍完全相同，使用稳定用户 ID 排序，保证结果可重复。

战斗中的排行榜是预计排名；只有 Boss Settlement Snapshot 冻结后的榜单才是最终结果。页面需要显示当前预计 MVP 名额、获奖线、前 10 名以及当前用户自己的名次。

## 9. 击杀与结算

Boss 血量在本地同步结果中达到零后：

1. Boss 状态变为 `settling`，页面显示“正在确认最终战报”。
2. 服务端执行最终权威同步，并按发生时间重放尚未分配的记录。
3. 冻结 Boss 血量、击杀时间、全部个人贡献、有效人数、MVP 名额和原始排名。
4. 创建 Boss Clear Reward 和 Boss MVP Reward 的固定发放记录。
5. 低价值自动奖励进入交付队列，高价值奖励进入审核队列。
6. 若还有下一只 Boss，则从零贡献开启下一战。
7. 若最后一只 Boss 被击败，活动进入 `cleared`，剩余月份不再产生 Raid Damage。

月末仍未击败的当前 Boss 不发物质奖励，伤害不跨月；页面保留参战记录、最终血量、排名和纪念标识。

## 10. 奖励体系

### 10.1 两层奖励

**Boss Clear Reward** 面向该 Boss 的所有 Effective Raiders，承担协作激励。只允许配置小额额度或活动绑定抽奖卡。

**Boss MVP Reward** 面向该 Boss 排名最高的前 N 名，承担竞争激励。允许配置大额额度、活动绑定抽奖卡、订阅套餐和专属限时倍率。

第 1、2、3 名分别配置奖品。实际有效参战人数只解锁其中前 N 个名次，未解锁名次不产生奖励成本。

### 10.2 奖品类型与上线阶段

| 奖品 | 使用范围 | 一期 | 发放语义 |
|---|---|---:|---|
| 额度 | Clear / MVP | 是 | 通过远端 admin balance 增加余额，使用幂等键 |
| 活动抽奖卡 | Clear / MVP | 是 | 绑定管理员选定且尚未结束的摇摇乐活动 |
| 订阅套餐 | MVP | 二期已实现 | 指定分组和天数，保留并延长已有有效期 |
| 专属限时倍率 | MVP | 二期已实现 | 指定用户、分组、绝对倍率、时长、优惠用量上限和冲突备用额度 |

一期不提供“通用抽奖卡”。发布 Boss 活动时，抽奖卡奖品必须选择一个有效的 Shake & Win Campaign，且该活动结束时间必须晚于预计发奖时间；不满足时禁止发布。

订阅奖励不得从获奖当天覆盖已有套餐。相同分组存在有效订阅时，新到期日应基于现有到期日增加奖励天数；若上游不能证明安全延长，则转人工交付，不能损失用户原有天数。

### 10.3 限时倍率权益

限时倍率不是简单的“写入后到期恢复旧值”，而是一项独立权益：

- 奖品配置绝对倍率，例如 `0.8x`，而不是“降低 0.2”。
- 必须同时配置有效时长和优惠用量上限，任一先到即结束。
- 生效倍率取基础倍率、人工专属倍率和所有有效奖励倍率中的最低值。
- 已有更优临时倍率时，新权益排队且暂不计时。
- 已有更优永久人工倍率时，发放发布时预先配置的备用额度奖励。
- 到期后重新计算剩余权益，不能盲目写回历史快照。
- 远端倍率被人工修改且与本地权益预期冲突时，暂停自动写入并报警。

示例奖品：`指定分组 0.8x，7 天，最多覆盖原价 500 额度；备用奖励 50 额度`。

### 10.4 发放与审核

每个奖品都配置 `自动发放` 或 `审核后发放`：

- Boss Clear Reward 默认自动发放。
- 小额额度和抽奖卡默认自动发放。
- 超过管理员阈值的额度默认审核。
- 订阅套餐和限时倍率默认审核。

奖励由服务端自动生成发放记录，用户无需抢领。交付失败保持原奖品和原获奖人，使用同一奖励 ID 幂等重试，不能重选奖品。

审核只能判断身份与作弊，不能随意更换获奖人或奖品。若交付前确认作弊，记录取消原因并将名额顺延给下一位有效参战者；原始排名和最终获奖名单都必须保留。已交付奖励的追回属于独立运营决策，不能直接改写结算记录。

## 11. 奖励预算

每月设置一个 Raid Reward Budget。所有奖品都必须有内部成本值，无法估值的奖品不能发布。

单只 Boss 的最大有效参战人数按下式估算：

```text
最大有效参战人数 = ceil(Boss 血量 / 有效参战门槛)
```

最坏奖励成本至少包括：

```text
Clear Reward 单人成本 × 最大有效参战人数
+ 在该人数下可解锁的 MVP 第 1–3 名成本
```

月度最坏成本为所有 Boss 最坏成本之和。额度按面值计成本；抽奖卡使用运营配置的内部成本；订阅套餐使用套餐内部成本；限时倍率使用其最大优惠补贴成本，不得只按天数估算。

发布前必须满足：

- 所有奖励已有明确交付目标和成本；
- 最坏成本不超过月度预算；
- 抽奖卡目标活动有效；
- 限时倍率含用量上限和备用奖品；
- 高价值奖励已配置审核方式。

活动发布后，已承诺奖励必须足额履约，不能因为实际成本升高而改成先到先得、缩奖或临时替换。

## 12. 反作弊与公平性

- 只接收带稳定远端 ID 的权威用量记录，并按连接和远端 ID 去重。
- 用户必须在活动开始前注册，避免活动中批量创建小号凑人数。
- 一个稳定用户 ID 的所有 API Key 合并，不能分 Key 占多个名额。
- 内部、测试和运营账号由发布配置明确排除。
- 排名和获奖依据服务端快照，前端不得提交伤害、击杀或名次。
- 高价值奖励交付前可检查异常账号关联、用量模式和退款/冲正事实。
- 取消资格必须有操作者、时间、原因和证据引用。
- 不得在后台直接编辑个人贡献；数据纠正必须从权威用量重放或建立补偿记录。

公开排行榜只显示脱敏昵称，例如 `ka***23`。本人可见自己的完整名次和数据；管理员后台可见完整身份与用量证据。

## 13. 互动战斗页面

### 13.1 视觉方向

整体采用“赛博中转站防御战”：当前 Boss 是侵入中转网络的巨大核心，用户的真实 API 消耗转换为网络武器伤害。Boss 必须是首屏视觉中心，而不是把活动做成普通数据卡片页。

一期提供 5–8 套内置 Boss 位图素材。管理员可选择素材并配置 Boss 名称、称号、等级、血量、奖励和主题分组，不允许任意上传图片。实现时为桌面和移动端准备稳定比例的素材裁切，避免 Boss、血条和操作区互相遮挡。

### 13.2 首屏信息层级

1. 活动月份、当前 Boss 等级和名称。
2. Boss 主体场景、血条、剩余血量和全站伤害。
3. 主题分组及加成倍率。
4. 当前预计 MVP 名额、有效参战人数和距离下一名额所需人数。
5. 未参战用户的“加入战斗”主操作；已参战用户显示个人贡献和当前排名。
6. “上次同步时间”，明确伤害可能延迟约 60 秒。

首屏下方露出战报或排行榜的一部分，提示页面可继续滚动，但不放营销式介绍页。

### 13.3 战斗反馈

- 前端每 5–10 秒刷新本地活动状态。
- 后端权威用量同步一期维持最多约 60 秒延迟。
- 检测到血量减少后，按本次差量播放能量束、Boss 受击、屏幕震动、粒子和伤害飘字。
- 若一次刷新包含大量记录，最多逐条播放若干次，其余合并显示为“本轮 N 次攻击，共造成 X 伤害”，避免动画堆积。
- 自己产生的新伤害使用更明确的命中反馈，并拆分显示实际消耗和主题加成。
- Boss 接近击杀时进入警戒表现；确认击杀后播放破甲/崩解动画，再进入结算界面。
- 动画只呈现服务端差量，不生成虚假攻击或预扣血量。

音效默认关闭，由用户主动开启；遵守 `prefers-reduced-motion`，降低震动、闪烁和粒子数量。页面失焦时停止高频动画，恢复后直接对齐服务端状态。

### 13.4 辅助区域

**全站战报**：滚动展示最近的脱敏用户、伤害、主题加成和相对时间，不展示邮箱。

**贡献榜**：展示前 10 名、当前用户自己的名次、MVP 获奖线以及每人的贡献；列表在固定高度内滚动。

**奖励预览**：清晰区分全员击杀奖励与第 1–3 名 MVP 奖励，并根据当前有效人数标识已解锁名额。

**Boss 路线**：显示本月 Boss 1 到最终 Boss 的顺序、已击败状态和下一目标，不在战斗前隐藏奖励。

**个人战绩**：显示加入时间、实际消耗、主题加成、最终伤害、当前 Boss 排名及历次 Boss 结果。

### 13.5 页面状态

页面必须覆盖：未登录、未加入、战斗中、等待同步、Boss 结算中、Boss 已击败、全服通关、月末未击败、活动已结束、活动已中止、用量同步异常和奖励待审核/发放失败。

## 14. 管理后台

### 14.1 配置能力

- 创建或克隆月度活动；
- 设置月份、统一有效伤害门槛、总预算和排除账号；
- 排序 Boss，选择内置素材并配置名称、血量和主题分组；
- 配置 Clear Reward 和第 1–3 名 MVP Reward；
- 配置奖品成本、自动/审核发放和备用奖品；
- 预览最坏参与人数、MVP 名额和奖励成本；
- 以用户视角预览桌面和移动端页面；
- 校验通过后发布。

活动开始后配置全部只读。管理员可以提前中止、触发同步、处理奖励、取消作弊获奖资格或克隆配置到下月，但不能修改当前月的血量、门槛、倍率、排名和奖品。

### 14.2 运营与审计

- 显示远端用量同步游标、最后成功时间、错误和待处理记录数；
- 查看 Boss 血量构成和单条权威用量证据；
- 查看原始排行榜、最终获奖名单及顺延过程；
- 审核、重试、确认或作废奖励交付；
- 查看订阅延期和倍率权益的当前状态；
- 中止活动必须填写原因；
- 所有高风险动作写入审计日志。

## 15. 系统边界与数据模型

Boss 系统必须实现于 KaWang 项目和 `apikey.vsakura.top` 服务，不修改本地 `sub2api/` 参考项目。远端官方 Sub2api 仅作为权威用量和奖励交付系统；所有 admin API 调用通过本项目保存的远端管理员密钥完成，不能改用用户 token。

建议新增独立的 Boss 活动模块，核心数据包括：

| 数据 | 关键内容 |
|---|---|
| Raid Campaign | 连接、月份、状态、门槛、预算、已发布配置快照 |
| Raid Boss | 顺序、素材、血量、主题倍率、状态和击杀边界 |
| Raid Enrollment | 用户、加入时间、脱敏身份快照 |
| Raid Usage Record | 远端用量 ID、用户、分组、actual_cost、created_at、导入时间 |
| Raid Damage Assignment | 用量记录对应的 Boss、倍率和最终伤害 |
| Raid Contribution | Boss 级个人聚合读模型 |
| Boss Settlement Snapshot | 最终血量、有效人数、名额、原始排名和获奖者 |
| Raid Reward Grant | 固定奖品、收件人、审核、交付、重试和错误状态 |
| Raid Disqualification | 原排名、取消原因、证据和顺延对象 |
| Rate Entitlement | 用户、分组、绝对倍率、时长、用量上限和备用奖品 |

Boss 用量导入需要独立于摇摇乐是否正在运行。可以复用现有同步、游标和幂等模式，但不能依赖只在命中摇摇乐资格规则后才生成的数据。

Boss 击杀、结算快照、奖励记录和下一只 Boss 激活必须在本地事务中完成，避免出现“下一只已开但上一只没有固定获奖名单”的中间状态。

## 16. 接口建议

用户侧：

- `GET /api/sub2api/raid/bootstrap`：当前活动、Boss、个人状态、奖励和同步时间；
- `POST /api/sub2api/raid/enroll`：加入当前月份；
- `GET /api/sub2api/raid/leaderboard`：当前或历史 Boss 排行；
- `GET /api/sub2api/raid/battle-log`：最近聚合战报；
- `GET /api/sub2api/raid/history`：个人和全站历史结果。

管理员侧：

- 活动草稿创建、修改、克隆、校验和发布；
- Boss 及奖励配置；
- 手动触发用量同步和最终结算；
- 奖励审核、重试、确认和作废；
- MVP 取消资格与名额顺延；
- 活动中止和独立补偿记录。

所有写接口必须鉴权并写审计日志。用户接口沿用现有 Sub2api SSO 身份，不允许由客户端提交 `user_id`、伤害或名次。

## 17. 后台任务

1. **月度调度任务**：按北京时间开始活动、关闭伤害窗口并启动月末结算。
2. **用量同步任务**：最多约 60 秒同步远端权威用量，按远端 ID 去重。
3. **Boss 分配任务**：按 `created_at` 和稳定 ID 顺序分配伤害，检测击杀。
4. **Boss 结算任务**：最终追赶同步，冻结快照，创建奖励并激活下一只。
5. **奖励交付任务**：对自动奖励幂等发放，对失败奖励退避重试。
6. **倍率权益任务（二期）**：激活排队权益、统计优惠用量、处理到期并校验远端倍率；二期已接入。
7. **异常告警任务**：监控同步停滞、结算超时、奖励失败和倍率冲突。

## 18. 异常处理

| 场景 | 处理 |
|---|---|
| 远端用量接口不可用 | 暂停击杀确认，保留当前血量，页面显示同步延迟 |
| 同一用量重复返回 | 以连接和远端用量 ID 幂等忽略 |
| Boss 达零后仍有同批记录 | 按发生时间和稳定 ID 排序，单条不可拆分 |
| 月末最后一批尚未同步 | 在 10 分钟结算窗口补记月末前记录 |
| 结算后出现更早回填记录 | 不改写快照，进入异常审计和独立补偿 |
| 自动额度发放超时 | 奖励保持 pending，使用同一幂等键重试 |
| 抽奖卡目标活动已失效 | 发布前阻止；运行期异常则转人工处理 |
| 订阅无法安全延期 | 不覆盖原订阅，转人工发放 |
| 倍率遇到更优永久倍率 | 发放预先配置的备用额度奖励 |
| 作弊用户被取消资格 | 保留原排名，名额顺延至下一位有效用户 |
| 活动被中止 | 已结算奖励继续履约，当前 Boss 不正常派奖 |

## 19. 数据指标

### 19.1 核心效果指标

- 当月有效真实消耗及相对过去三个月同周期的增长率；
- 参战人数、有效参战人数和有效转化率；
- 指定主题分组的消耗占比及增长率；
- 各 Boss 击杀耗时、通关率和月末剩余血量；
- 人均贡献、中位数贡献及前 3 名贡献占比；
- Boss Clear Reward 覆盖人数和 MVP 名额解锁率。

### 19.2 经济指标

- 已承诺、待审核、已交付和失败奖励成本；
- 实际奖励成本 / 增量真实消耗；
- 限时倍率最大补贴、实际补贴和用量上限消耗；
- 每种奖品的履约成功率和人工处理成本。

### 19.3 健康指标

- 用量同步延迟和错误率；
- 重复记录拦截数；
- 高价值奖励审核通过率；
- 取消资格和疑似小号比例；
- 页面刷新成功率、动画性能和移动端错误率。

若前 3 名长期贡献超过全站伤害的绝大部分，而有效参与人数没有增长，应调低单纯排名奖励占比、提高共享奖励价值或增加分段个人里程碑，而不是继续加大第一名奖品。

## 20. 上线分期

### 20.1 上线前模拟

使用最近三个月权威用量进行离线回放，验证：

- 2,000 / 4,000 / 7,000 / 11,000 血量是否符合预期节奏；
- 门槛 `10` 下的有效人数和 MVP 名额；
- 指定分组倍率对通关速度和排名集中度的影响；
- 最坏奖励预算是否可承受；
- 月末延迟同步、并发击杀和同分排序。

### 20.2 一期

- 单连接、北京时间自然月；
- 主动加入、真实用量伤害、Boss 连续推进；
- 主题分组伤害倍率；
- 有效参战门槛和浮动 MVP 名额；
- 额度与活动绑定抽奖卡；
- 自动/审核发放、预算校验、反作弊顺延；
- 赛博 Boss 页面、5–8 套内置素材、5–10 秒页面刷新；
- 最多约 60 秒权威伤害延迟；
- 完整后台、审计、历史榜和异常状态。

### 20.3 二期（当前实现范围）

- 订阅套餐奖励及安全延期；
- 带时长和优惠用量上限的专属分组倍率权益；
- 权益排队、备用奖励、到期重算和冲突告警；
- 基于一期数据调整 Boss 血量、门槛和奖品结构。

跨连接全站 Boss、SSE/WebSocket 实时推送、用户自定义 Boss 素材和无限关卡均不进入前两期，只有一期数据证明活动有效后再评估。

## 21. 一期验收标准

1. 同一远端用量记录重复同步不会重复造成伤害。
2. 加入前用量、非活动月份用量和次月用量不会计入。
3. 指定分组倍率同时影响血量、个人贡献、门槛和排行，账单不受影响。
4. 单条过量伤害全部归当前 Boss，溢出不进入下一只。
5. 每只 Boss 的贡献从零开始，历史结算快照不可修改。
6. `9 / 10 / 19 / 20 / 29 / 30` 名有效参战者分别产生 `0 / 1 / 1 / 2 / 2 / 3` 个 MVP 名额。
7. 同分排名在重复计算后结果一致。
8. 未击败 Boss 月末不发正常物质奖励，已击败 Boss 奖励继续履约。
9. 最坏奖励成本超过预算时无法发布活动。
10. 自动奖励失败可幂等重试，高价值奖励未经审核不会发出。
11. 取消作弊获奖者后名额顺延，原始排名和原因仍可审计。
12. 页面所有伤害动画都来自服务端新增差量，并展示上次同步时间。
13. 移动端首屏能看到 Boss、血条、参战状态和个人贡献，榜单可滚动且不遮挡。
14. 活动中止不会改写已结算 Boss，也不会为当前 Boss 伪造奖励。

## 22. 首月运营建议

- 活动名称使用“全域突袭 · 第一赛季”一类可延续命名。
- 首月只开放 4 只 Boss，主题倍率最高不超过 `1.5x`。
- 有效伤害门槛从 `10` 起步，发布前用历史数据回放确认。
- Clear Reward 保持小而确定，MVP Reward 保持有吸引力但不超过预算。
- 首月高价值额度奖励全部审核，验证反作弊流程后再放宽自动发放阈值。
- 活动页提前展示完整血量、名额公式、奖励和同步延迟，不做隐藏概率。
- 月末复盘重点看真实消耗增量、主题分组迁移、有效人数和头部贡献集中度，而不只看是否通关。

这套设计的关键不是让用户“花额度抽奖”，而是让每一笔真实使用都成为可见的团队推进，同时用透明、有限且可审计的排名奖励鼓励额外贡献。
