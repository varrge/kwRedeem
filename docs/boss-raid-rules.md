# 月度 Boss 突袭：统一规则

> 这是 Boss 突袭的当前唯一规则入口。本文整合已确认的产品规则、首期运营参数和已实现的二期奖励能力。
> 详细背景、推导和历史讨论见 [boss-raid-campaign-plan.md](./boss-raid-campaign-plan.md)；若两份文档冲突，以本文为准。

> **2026-08-31 PVE 规则更新：以下规则优先于本文后续保留的第一期 MVP 历史方案。**

## 当前 PVE 奖励规则

- 兼容迁移按活动锁定奖励模式：升级时数据库中已经存在的活动标记为 `legacy_mvp`，继续按原共享奖励、动态 MVP、资格顺延和原战场页面完整结算；升级后新建的活动固定为 `pve`。
- 奖励模式不接受管理 API 修改。活动发布后继续锁定全部规则，不能把进行中的 `legacy_mvp` 活动切成 PVE，也不能把新 PVE 活动切回 MVP。
- 月度 Boss 战改为全服协作 PVE；贡献榜只展示战绩，不再决定奖励，也不再生成新的 MVP 奖励。
- 每只 Boss 只配置一项击杀奖励。现支持参战额度、参战抽奖卡，以及新的
  `global_recharge_multiplier`（全站充值倍率）。
- 配置全站充值倍率时，Boss 击败并完成稳定结算后立即调用 Sub2api
  `PUT /api/v1/admin/payment/config`，只更新 `balance_recharge_multiplier`。
- 活动层将全站充值倍率限制为大于 `0` 且不超过 `5x`，防止管理员误配置超高倍率；这是本系统的
  产品安全上限，不是 Sub2api 接口上限。
- 全站充值倍率面向该 Sub2api 连接的全部用户，包括未报名和未入榜用户。
- 连续击败多只配置了全站充值倍率的 Boss 时，后击败 Boss 的倍率覆盖前一只；不叠加。
- 全站倍率按 Sub2api 连接维护单一“期望倍率”并串行对账。旧 Boss 重试时只会重新应用当前最新期望值，
  不能覆盖后续 Boss；跨月旧记录重试也不能把新月份已经生效的倍率错误恢复成 `1x`。
- 对账会通过官方支付配置 GET 接口回读远端实际倍率。本地即使显示已应用，定时维护仍会校验；若旧请求
  延迟落地或有人在 Sub2api 后台改动导致漂移，会重新写入当前权威倍率。
- 全站倍率不允许“确认到账”或“作废”。即使远端写入成功后本地超时，记录仍必须留在对账链路中，
  确保月末一定尝试恢复或应用新月份的权威倍率。
- 所有全站充值倍率都以活动对应的北京时间自然月月末为统一截止点。维护任务最多约 60 秒内将倍率
  强制恢复为 `1x`，不会沿用到下个月。
- 月末恢复失败会记录为 `revert_failed` 并保留错误，管理员可在奖励履约页重试；成功后状态为
  `expired`。
- 中止活动不撤销已经击败 Boss 的奖励；已经生效的全站充值倍率仍在该自然月月末恢复 `1x`。
- `legacy_mvp` 活动仍可产生和履约 MVP 奖励、执行取消资格与顺延；其历史记录永久保留。只有新 PVE
  结算不再产生这些记录。

下文涉及“动态 MVP 名额、MVP 奖励、资格顺延”的内容适用于 `legacy_mvp` 活动，不适用于新 PVE 活动。

## 0. 当前版本

| 项目 | 规则 |
|---|---|
| 版本 | 2.0 PVE |
| 更新日期 | 2026-08-31 |
| 活动周期 | 每个自然月一次 |
| 时区 | `Asia/Shanghai` |
| 首期范围 | 一个 Sub2api 连接 |
| 首期计费倍率 | 全部 `1.0x` |
| 有效伤害门槛 | `10` |
| 首期运营目标 | 至少 10 名有效参战者；Boss 1 在活动开始后 15 天内击败 |

“至少 10 人”和“15 天内击败”是首期运营目标及 MVP 解锁参考，不是未达成即自动中止的硬门槛。活动仍按月末规则继续或结束。

## 1. 一句话规则

用户主动加入后，正常 API 使用产生的真实 `actual_cost` 自动转为 Boss 伤害；全体有效参战者共同获得共享奖励，贡献排名靠前者在此基础上额外获得浮动名额的 MVP 奖励。

```text
活动伤害 = 权威用量 actual_cost × 活动倍率
首期活动倍率 = 1.0x
```

活动页面只展示服务端确认的事实，不负责制造伤害、扣款或决定奖励。

## 2. 活动范围与周期

- 每月 1 日 00:00:00 开始，次月 1 日 00:00:00 停止接收新伤害。
- 月末后保留 10 分钟最终同步窗口，只补同步本月已经发生的权威用量。
- 当前一期只聚合一个 Sub2api 连接，不跨连接合并用户或伤害。
- 活动从 Boss 1 开始，击败后连续开启下一只。
- 每只 Boss 独立结算，结算后个人贡献归零。
- 进度不跨月；下个月重新创建或发布新活动，用户重新加入。

### 活动状态

| 状态 | 含义 |
|---|---|
| `draft` | 可编辑草稿 |
| `scheduled` | 已发布，等待开始 |
| `active` | 可加入、可同步、可查看排行 |
| `settling` | 最终同步或月末结算，只读 |
| `cleared` | 最后一只 Boss 已击败 |
| `ended` | 月份结束，保留历史结果 |
| `aborted` | 活动中止，当前 Boss 不正常派奖 |

## 3. 参战资格

1. 用户账号必须在活动开始前注册。
2. 用户可在活动期间任意一只 Boss 存活时主动加入。
3. 只计算加入之后发生的合格用量，不追溯加入前消费。
4. 加入一次后，本月后续 Boss 自动保持参战状态。
5. 同一稳定 Sub2api 用户 ID 下的 API Key 合并统计。
6. 内部账号、测试账号、管理员配置的排除账号不计伤害，也不能获奖。
7. 报名不等于有效参战；是否有效由每只 Boss 的个人伤害门槛决定。

## 4. 伤害与计费规则

### 4.1 权威来源

伤害只来自官方 Sub2api 管理用量接口的逐条记录。记录必须有：

- 稳定远端用量 ID；
- `user_id`；
- `actual_cost`；
- 权威 `created_at`；
- 可选 `group_id`、`subscription_id`。

不使用余额前后差额推算伤害，也不直接读取摇摇乐消费表代替全站用量总账。

### 4.2 首期口径

- 所有 Boss 的活动倍率固定为 `1.0x`。
- 首期不配置主题分组加成，不配置中转站额外倍率。
- 活动攻击不额外扣余额；用户只需正常使用 API。
- `actual_cost` 已包含真实计费倍率，活动不重复计算。
- 充值、余额兑换码、邀请返利、管理员调账和世界杯余额变动不计伤害。

### 4.3 记录分配

- 按权威 `created_at` 从早到晚分配，不按本地同步时间分配。
- 同一时间按稳定远端用量 ID 排序。
- 单条用量不可拆分。
- 一条用量只能计算一次，按连接和远端 ID 去重。
- 若当前 Boss 剩余 5 点血量而单条用量造成 100 点伤害，100 点全部归当前 Boss，95 点不顺延。
- 下一只 Boss 只接收击杀边界之后发生的用量。
- 页面可同时显示“实际消耗”和“活动伤害”；首期两者相同。

## 5. 首期 Boss 配置建议

以下是首期建议草案，正式发布前仍需在后台选择月份并锁定配置。

| 顺序 | Boss | 血量 | 倍率 | 定位 |
|---:|---|---:|---:|---|
| 1 | 封锁者 | 2,000 | 1.0x | 15 天内击败，建立参与感 |
| 2 | 装甲核心·利维坦 | 4,000 | 1.0x | 第一只击败后开启 |
| 3 | 棱镜母体 | 7,000 | 1.0x | 中段协作目标 |
| 4 | 零号主机 | 11,000 | 1.0x | 月度最终目标 |

首期不要根据实时进度临时加血、减血或修改倍率。若历史用量无法支持 Boss 1 在 15 天内击败，应在发布前调整血量，而不是活动中途改规则。

## 6. 有效参战、共享奖励与 MVP

### 6.1 有效参战

- 每只 Boss 的统一有效伤害门槛为 `10`。
- 贡献达到 `10`（包含活动倍率后的最终伤害）才算该 Boss 的有效参战者。
- 未达到门槛的贡献仍然会削减 Boss 血量，但不计入有效人数、不获得共享奖励、不进入 MVP 候选。
- 每只 Boss 重新计算有效参战人数和个人贡献。

### 6.2 共享奖励

共享奖励发给该 Boss 的所有有效参战者。

- MVP 也是有效参战者，因此 **MVP 同样获得共享奖励**。
- MVP 的总奖励 = 共享奖励 + 对应名次的 MVP 奖励。
- 只报名或只产生低于门槛的伤害，不获得共享奖励。
- 每只 Boss 独立发放，不能用 Boss 1 的资格领取 Boss 2 奖励。
- 共享奖励可配置小额额度或活动绑定抽奖卡。

例：20 名有效参战者时，20 人都获得共享奖励，第 1、2 名再额外获得 MVP 奖励。

### 6.3 MVP 名额

```text
MVP 名额 = min(3, floor(有效参战人数 / 10))
```

| 有效参战人数 | MVP 名额 |
|---:|---|
| 0–9 | 0 |
| 10–19 | 1：第 1 名 |
| 20–29 | 2：第 1、2 名 |
| 30+ | 3：第 1、2、3 名 |

少于 10 人时仍可正常击败 Boss，所有有效参战者仍拿共享奖励，但没有 MVP 奖励。

### 6.4 排名

1. 贡献降序。
2. 贡献相同时，较早达到最终贡献值者优先。
3. 权威时间仍相同时，按稳定用户 ID 排序。
4. 战斗中的排行榜是预计榜单；结算快照中的榜单是最终榜单。

## 7. 奖励类型

| 奖励类型 | 共享奖励 | MVP 奖励 | 发放说明 |
|---|---:|---:|---|
| 额度 | 支持 | 支持（二期可选） | 首期 MVP 不使用额度；额度发放使用远端 admin balance 和幂等键 |
| 活动抽奖卡 | 支持 | 支持 | 必须绑定有效的摇摇乐活动 |
| 订阅套餐 | 不支持 | 支持（二期） | 指定分组和奖励天数 |
| 专属限时倍率 | 不支持 | 支持（二期） | 指定分组、绝对倍率、时长、用量上限和备用额度 |

### 二期订阅套餐

- 同分组有有效订阅时，在原有效期结束时间上延长奖励天数。
- 没有有效订阅时，新建指定分组的订阅。
- 无法安全延期时进入人工发放，不能损失用户原有天数。
- 不从获奖当天覆盖或重算用户已有套餐。

### 二期限时倍率

- 使用绝对倍率，例如 `0.8x`，不配置“降低 0.2”。
- 必须配置持续天数、优惠用量上限和冲突备用额度。
- 时间或优惠用量任一先到即结束。
- 已有更优临时倍率时，新权益排队且不开始计时。
- 已有更优永久倍率时发放预先配置的备用额度。
- 到期时先检查远端当前倍率；只有仍是本权益写入的倍率，才允许恢复原值。
- 远端被人工修改时暂停自动覆盖并保留异常记录。

## 8. 结算、发放与反作弊

### 8.1 Boss 结算

1. 本地重算发现 Boss 达到零血，状态变为 `settling`。
2. 服务端执行最终权威同步。
3. 连续两次同步确认没有更早的新记录后，冻结结算快照。
4. 快照包括击杀时间、全部贡献、有效人数、MVP 名额和原始排名。
5. 生成固定共享奖励记录和 MVP 奖励记录。
6. 有下一只 Boss 时，从零贡献开启下一只；没有下一只时活动变为 `cleared`。

### 8.2 奖励履约

- 每个奖励记录固定收件人、奖品、成本和发放模式。
- 小额额度和抽奖卡可自动发放。
- 高价值额度、订阅和限时倍率建议审核后发放。
- 发放失败保持原奖励和原获奖人，使用同一奖励 ID 幂等重试。
- 不因发放失败重新抽奖、不临时换奖。

### 8.3 取消资格与顺延

- 取消资格必须记录操作者、时间、原因和证据。
- 已发放奖励不能直接改写结算记录。
- 发放前取消时，名额顺延给下一名有效参战者。
- 原始排名、取消原因和最终获奖名单全部保留。

### 8.4 月末未击败与中止

月末未击败当前 Boss：

- 当前 Boss 不发正常共享奖励和 MVP 奖励；
- 伤害不跨月；
- 保留参战记录、最终血量、排名和纪念标识；
- 已击败 Boss 的奖励继续履约。

活动中止：

- 进入 `aborted`，不是正常 `ended`；
- 当前 Boss 不产生正常奖励；
- 已结算 Boss 的固定奖励继续履约；
- 补偿必须另建审计记录，不能伪造击杀或修改排行榜。

## 9. 预算规则

- 管理员设置月度总预算。
- 每个奖品必须配置内部成本。
- 发布前计算所有 Boss 的最坏成本，超过预算不能发布。
- 共享奖励按最大有效参战人数计算。
- MVP 按当时可解锁的最多 3 个名额计算。
- 限时倍率取主成本与备用额度成本的较高值。
- 发布后不能缩奖、改奖或改成先到先得。

首期奖励模板（发布前仍需绑定具体摇摇乐活动并填写抽奖卡内部成本）：

| Boss | 共享奖励/人 | MVP 1 | MVP 2 | MVP 3 |
|---|---:|---:|---:|---:|
| LV.1 | 0.20 额度 | 低级抽奖卡 x3 | 低级抽奖卡 x2 | 低级抽奖卡 x1 |
| LV.2 | 0.30 额度 | 低级抽奖卡 x6 | 低级抽奖卡 x4 | 低级抽奖卡 x2 |
| LV.3 | 0.50 额度 | 低级抽奖卡 x9 | 低级抽奖卡 x6 | 低级抽奖卡 x3 |
| LV.4 | 1.00 额度 | 低级抽奖卡 x12 | 低级抽奖卡 x8 | 低级抽奖卡 x4 |

首期 MVP 不发余额，全部使用活动绑定的低级抽奖卡并自动发放。数量规则为：第一名 `Boss 等级 x3`、第二名 `Boss 等级 x2`、第三名 `Boss 等级 x1`。每张卡必须绑定一个结算窗口结束后仍有效的摇摇乐活动，并按该活动实际奖池填写内部成本。共享额度的最坏成本为 `1,610`，默认月度预算设为 `2,800`，为抽奖卡保留 `1,190` 成本空间；最终能否发布以后台校验为准。

## 10. 页面规则

页面采用 Boss 为视觉中心的伪 3D 战场：大背景、中央 Boss、稳定的受击反馈，数据放在轻量模糊小框中。

首屏必须展示：

- 活动月份、当前 Boss 等级、名称和称号；
- Boss、血条、剩余血量、全站伤害；
- 有效参战人数和当前 MVP 名额；
- 用户的加入状态、个人伤害和排名；
- 上次同步时间，并明确最多约 60 秒延迟；
- 当前 Boss 的共享奖励和 MVP 奖励预览。

交互规则：

- 用户点击加入，不提供额外扣款的攻击按钮。
- 页面每 5–10 秒刷新展示状态；权威用量同步由服务端维护。
- 血量减少时播放服务端差量对应的受击、粒子和数字飘字。
- 不预扣血、不生成虚假攻击、不伪装逐请求实时战斗。
- 音效默认关闭，支持减少动态效果。
- 必须覆盖未登录、未加入、战斗中、等待同步、结算中、已击败、全服通关、月末未击败、已结束、已中止和奖励失败状态。

## 11. 管理后台规则

管理员可以：

- 创建或克隆月度活动；
- 选择唯一 Sub2api 连接；
- 设置月份、门槛、预算、排除账号；
- 配置 Boss 顺序、内置素材、血量、倍率和奖励；
- 预览最坏人数、MVP 名额和成本；
- 发布、触发同步、查看历史榜和处理奖励；
- 取消作弊资格、处理顺延和中止活动。

发布后：

- 当前月配置只读；
- 不能修改血量、门槛、倍率、排名规则或奖品；
- 所有高风险操作写入审计日志。

## 13. 首期验收指标

- 至少 10 名有效参战者；
- Boss 1 在前 15 天内击败；
- 重复同步不重复计伤或发奖；
- 加入前用量不计入；
- 单条过量伤害不跨 Boss；
- MVP 名额在 `9 / 10 / 19 / 20 / 29 / 30` 人边界正确；
- MVP 同时收到共享奖励和 MVP 奖励；
- 月末未击败 Boss 不发正常物质奖励；
- 奖励失败可幂等重试；
- 取消资格后正确顺延，且历史榜不可篡改；
- 页面无水平溢出、无虚假实时攻击和明显闪烁。

## 14. 暂不进入本规则的能力

- 多 Sub2api 连接跨站聚合；
- SSE/WebSocket 逐请求实时推送；
- 任意上传 Boss 图片；
- 无限 Boss 路线；
- 用户自定义奖励脚本；
- 用主题倍率改变真实账单；
- 通过攻击按钮直接扣除余额。
