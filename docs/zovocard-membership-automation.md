# ZovoCard 会员自动化

当前会员付款由「会员自动化」页签中的协议站点执行。ZovoCard 使用 `spacex_gpt_direct_v1`，站点地址为 `https://zovocard.com/openapi/v1`。本文对应 `spacexcard-openapi (3).md`。

## 协议变化

| 项目 | 当前行为 |
| --- | --- |
| 可售套餐 | 同时要求 `registry` 收录、`purchasable=true`、关联 `plans` 配置 `enabled=true`；支持 Plus、5x、20x、50x |
| 付款地区 | 从 `payment_regions` 同步，报价金额按返回的最小货币单位解释，JPY 不固定除以 100 |
| 新订阅 | 先预检、校验套餐和金额范围，再准备卡片；同一预检对象用于建单 |
| 已有低档会员 | 查询 `upgrade-quotes`，使用目标档位的新令牌、账单币种和差价，以 `direct` 建单；不先购买低档套餐 |
| 升级资金 | `funding_usd_minor` 是卡内资金估算，不是应付差价；缺少估算时停止，估算不得超过映射单笔预算 |
| 报价有效期 | 新购最多 10 分钟、升级最多 5 分钟；过期且尚未提交才可重新预检；令牌只提交一次 |
| 付款完成 | 使用远端最终账单金额；升级差价不与新订阅全价范围比较，仍要求目标套餐、币种和完成状态正确 |
| 原卡复用 | 相同站点、远端预检确认的账号及历史成功订单可提名原卡；允许跨档位复用，不清空累计用量 |
| 卡片约束 | 排除卡、占用、冷却、待对账状态仍生效；卡片用量格式异常时停止注资；远端再次判断最终资格 |
| 未知结果 | 按原 `client_request_id` 查询原订单；查询失败或未找到不重新付款、不换卡重试 |

原卡复用只使用远端预检确认的身份，数据库保存按站点隔离的 HMAC。旧订单没有该身份记录时，不会仅凭客户提交的邮箱放宽卡片容量限制。50x 的协议没有独立用量桶，本地继续限制映射容量，远端负责最终资格校验。

普通新购保留原有整卡预存/单槽额度规则。差价升级优先使用已有余额；需要充值时按资金缺口和产品最低充值额计算，新开卡按资金估算和产品最低开卡额计算，两者均受映射单笔预算约束。卡台手续费和站点服务费另计。

未知开卡或充值结果也会阻止后续付款，即使查询时卡内余额已经增加。通用 HTTP 400 和中文拒绝消息不作为「肯定未扣款」的证据。

## 部署后配置

1. 在会员自动化中同步现有 ZovoCard 站点，确认下发的套餐和地区。
2. 在付款卡台配置中维护 SpaceX Card 凭据；此配置与站点 API Key 独立保存，不启用旧 Go 付款。
3. 如需销售 50x，创建商城交付类型为「会员自动化」、套餐为 `x50` 的商品映射，然后绑定远端 `pro_50x`。
4. 为各映射配置地区、全价范围、卡容量、资金金额和日风险上限。单笔预算为资金金额除以容量；差价超过预算时不会自动注资。
5. 同步后套餐下架或地区发生不兼容变化时，相关映射会暂停，需要核对后再启用。

这次协议适配不自动修改商城售价，也不把已有低档会员作为新商品重新定价。CDK 仍使用既有套餐范围，差价升级仅用于直接充值。

## 旧 Go / Python 付款退役

旧入口不再接收或推进新付款，旧写入接口返回 `410 LEGACY_MEMBERSHIP_RETIRED`。历史订单、资金记录、卡片凭据及必要的补偿审计保留，已有订单不自动转换成新协议订单。

已有 systemd 安装在升级后保留无付款能力的兼容进程，满足旧升级器的版本及心跳检查；它们不启动付款处理器、执行器桥接或浏览器。升级前检查旧结账命令，存在 `queued`、`leased`、`action_required` 时阻止替换旧服务，先核对在途付款。首次升级沿用现有固定部署 helper 和 sudo 授权，不自动删除服务。

验证使用临时数据库和模拟 HTTP/DNS，不会发起真实开卡、充值或会员付款。
